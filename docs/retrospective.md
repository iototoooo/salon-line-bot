# 振り返り：美容室向け LINE bot＋AI 自動応答システム

- 対象期間：2026-11-10〜2026-11-14（学習用の模擬受託案件。架空の店舗）
- 作成：2026-11-14
- 方針：記録（Git の履歴・`docs/` の資料・本番の読み取り専用の確認結果）に基づいて書く。記録のないこと（作業時間など）は推測しない

## 1. 技術面

### 良かった点

- **誤回答を「仕組み」で防いだ。** AI への指示だけに頼らず、出力をコードで検査する（`src/lib/ai/guard.ts`）。登録外の金額・電話番号・URL、空き状況や予約可否の断定を検出し、「確認が必要です」に差し替える。予約の案内は AI の文章を使わずコードで組み立てる
- **誤送信を「既定値」で防いだ。** LINE への返信は `LINE_REPLY_MODE=live` を明示しない限り送らない（dry-run）。管理画面の書き込み・一斉配信・AI の回答テストは安全スイッチ（既定 OFF）。一斉配信はテスト送信・送信可能数の確認・確認文言・二重送信の防止（DB の条件付き更新＋再送キー）を省略できない
- **DB で整合性を守った。** 全テーブルで RLS、重複の判定・利用回数・通知のまとめ送信は DB 関数とロックで直列化。本番の権限・設定は `verify.sql`（136 項目）で確認できる
- **テストの層を分けた。** 単体テスト 989 件（外部 API はモック）、DB は PGlite に全マイグレーションを適用して検証、管理画面は偽の Supabase に接続するブラウザ自動テスト 18 件。本番に接続しないことを設定と仕組み（通信先の制限）で保証した
- **本番作業で問題を見つけ、事故になる前に直した**（いずれも `docs/deployment.md` の記録あり）
  - Windows PowerShell 5.1 が、子プロセスに渡す値の先頭に BOM を付ける問題。環境変数の登録前にダミーの値で検出し、対策と自動の事前確認をスクリプトに入れた
  - Vercel のプロジェクトのフレームワークが未設定で、初回デプロイが `STATIC_BUILD_NO_OUT_DIR` で失敗。`vercel.json` に `framework` を指定して解消
  - Vercel CLI が `.gitignore` に追記した行が、`.env.example` を管理する設定を打ち消していた。元に戻した
  - Hobby（無料）の制約に合わせ、定期実行を Cron Jobs から Schedules に変更。定期削除の呼び出し口がなかったため、8 本目のマイグレーションを追加

### 課題

- **AI（Claude API）の実接続での確認が最後になった。** 完成判定の後に、管理画面の回答テストで主要 5 問（AC-01〜05）に合格したが、LINE 経由の AI 自動返信と AC-12（想定質問 20 問）などは未検証。最初の試行では安全スイッチの登録漏れで AI が呼ばれず、原因の調査に時間を使った
- README が完成直前まで create-next-app の初期状態のままだった
- Hobby の実行ログは保存期間が短く、後から確認できる範囲が限られた

### 改善策

- AI を使う機能は、早い段階で利用上限額を決めて少額で実接続し、主要な質問の結果を記録する（今回は `docs/submission.md` 3 の手順で実施）
- 環境変数の登録は、名前・登録先を一覧で確かめてから再デプロイする（登録用のスクリプトで扱うと漏れを防げる）
- README は最初のコミットで骨組みを作り、機能を追加するたびに更新する
- 確認に必要な結果は、アプリ側で件数・結果コードを DB に残す（今回、オーナー通知の結果は DB に残したが、定期削除の件数はレスポンスとログにだけ残した）

## 2. PM 面

### 良かった点

- **本番の操作をすべて段階に分けた。** 「準備 → 承認 → 実行 → 読み取り専用の検証」の順で行い、承認のない本番操作はしなかった（デプロイ・環境変数・DB の適用・LINE の送信）
- **前後比較できる検証の仕組みを作った。** `deploy-snapshot.sql`（13 項目）と `content-fingerprint.sql`（登録内容の指紋）で、本番のデータが意図せず変わっていないことを数字で確認した
- **基盤は無料の範囲に収めた。** LINE は今月 4 通（無料枠 200 通）、Vercel Hobby、Supabase Free。課金が必要な Claude API は、完成判定の後に管理画面の回答テストで主要 5 問の確認だけに使い（呼び出しは少数）、終了後に API キーを削除した。Claude API の費用の金額は記録していない（Anthropic Console で確認する）
- **範囲を絞った判断を記録に残した。** LINE アカウントは 1 つ（AC-23 の一部は自動テストで代替）、AC-22 は開発者本人がオーナー役、定期削除の初回確認は省略、など
- 受け入れ基準を「本番で確認／一部／自動テストで代替／未実施」に分け、確認していないものを完了と書かなかった（`docs/wbs.md` 6.4）

### 課題

- **作業時間を記録しなかった。** 見積もり 5.5 人日に対する実績工数を比べられない（期間は 5 日・コミット 41 件だが、工数ではない）
- 確認の手順・チェックリストが複数の資料に分かれ、全体の進み具合を一目で把握しにくかった
- 課題の納品チェックリストとの対応表を、最後にまとめて作った

### 改善策

- 作業の開始・終了の時刻を WBS の ID ごとに簡単に記録する（1 日の終わりに数分）
- 最初に納品チェックリストを `docs/` に置き、各作業の完了条件と対応させて進める
- 提出状況（`docs/submission.md`）を早めに作り、進捗のたびに更新する

## 3. Claude Code の活用面

### 良かった点

- **プロジェクトのルールを `CLAUDE.md` に書いて共有した。** 禁止事項（本番操作・課金・送信・push）、作業の順番（test → lint → typecheck → build）、回答の言語などを明文化し、作業のたびに守らせた
- **繰り返す作業をスクリプト・SQL にした。** 環境変数の登録（`scripts/vercel/register-env.ps1`・`register-cron.ps1`）、本番の確認用 SQL（`verify.sql`・`deploy-snapshot.sql`・`content-fingerprint.sql`）、取り消し用 SQL。どれもテストで安全条件を確認した
- **変更ごとに検証させた。** テスト・lint・typecheck・build、秘密情報のパターン検査、差分の確認を、コミットの前に毎回行った。資料（手順書・WBS・引き継ぎ資料）もコードと同時に更新した
- 公式ドキュメントで仕様を確認してから設定した（Vercel の Schedules・リージョン・`.vercelignore`、LINE の料金の数え方など）

### 課題（実際に起きたこと）

- 回答の言語のルールに反して、英語で報告したことが 3 回あった
- PowerShell が引数の `--` を取り除いたため、Vercel CLI がコマンドをデプロイと解釈しかけた（エラーで止まり、デプロイはされなかった）
- 定期削除の時刻を「毎時 17 分」と誤って説明した（正しくは毎日 03:17 JST）
- 比較用のスクリプトが日本語を読み違え、一致している値を「不一致」と表示した

いずれもその後の確認で発見し、訂正・再確認した。

### 改善策

- 報告の前に、言語・事実（数値・時刻）を見直す手順をルールに入れる
- 本番に影響しうるコマンドは、PowerShell の引数の扱い（`--` など）を事前に確かめ、まず読み取り専用のコマンドで試す
- 比較・判定は、可能な限りテストのあるスクリプトで行い、その場限りのコマンドに頼らない
